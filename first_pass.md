# Skia First-Pass Analysis

> **Snapshot**: Skia commit `ca229e3195` (2026-11-24) cloned at `../skia`.  
> **Upstream references cross-checked**: Chromium `skia/BUILD.gn`, `skia/features.gni`, `skia/config/SkUserConfig.h`; Skia's `gn/gn_to_bp.py`; AOSP `external/skia/Android.bp`, `frameworks/base/libs/hwui/Android.bp`, `frameworks/native/libs/renderengine/Android.bp`.  
> **Reproducibility**: All LoC/SLOC counts and usage matrices were generated by [`scripts/analyze_skia.py`](scripts/analyze_skia.py) (see [`scripts/README.md`](scripts/README.md) for methodology and exact commands).

---

## Executive Summary

1. **The "real" Skia library is ~568K SLOC (~800K total lines), not ~1.5M.** A naive count of the repository reports **1.53M SLOC (1.97M total lines)** across 9,523 code files, but **356K SLOC** is vendored Khronos Vulkan headers (`include/third_party/vulkan/`) and **607K SLOC** is tests, golden SkSL shader outputs, GMs, benchmarks, tools, docs, and experiments.
2. **GPU rendering dominates at 39% of production code — and legacy Ganesh is 2.1× the size of Graphite.** `src/gpu/` + `include/gpu/` total **221.4K SLOC**, split between legacy **Ganesh (142.7K SLOC)**, next-generation **Graphite (68.6K SLOC)**, and shared GPU infrastructure (**10.2K SLOC**). Retiring Ganesh removes ~25% of Skia's entire production codebase.
3. **Chrome and Android share 78.3% of Skia's production SLOC (445.2K SLOC)**, with Chrome building **85.3%** (plus 6.0K SLOC of Rust codecs still living under `experimental/`) and Android building **80.6%**.
4. **A Rust migration is already actively underway at Skia's untrusted-input boundary.** Skia already contains ~8.9K SLOC of Rust FFI/bridge code across Fontations (`src/ports/fontations/`), codecs (`rust/png`, `rust/bmp`, `experimental/rust_ico`, `experimental/rust_jpeg`), ICC color profiles (`rust/icc` / `moxcms`), and EXIF (`rust/exif`), plus CrabbyAvif in Android — with Chrome already shipping Rust PNG, BMP, ICO, ICC, EXIF, and Fontations.
5. **12.4% of production code (70.7K SLOC) is used by neither Chrome nor Android** — primarily `modules/canvaskit`, `modules/skparagraph`, `modules/svg`, `modules/skunicode`, native Metal (Ganesh + Graphite) and Direct3D 12 GPU backends, experimental Graphite sparse-strips/Vello prototypes, legacy Windows GDI / direct FontConfig font ports, and niche modules (`skplaintexteditor`, `bentleyottmann`, `audioplayer`). On top of that, ~7K SLOC of SkSL backend codegen (Metal everywhere; WGSL on Android) is compiled in via build-group bundling despite not executing at runtime.

## 2. How Skia Is Used in Chrome

Chrome does **not** use Skia's standalone `BUILD.gn`; Chromium maintains its own `//skia/BUILD.gn`, `//skia/features.gni`, `//skia/config/SkUserConfig.h`, and `//skia/ext/` wrapper layer that cherry-picks Skia's `.gni` filegroups.

### 2.1 Architecture & Integration Boundaries
- **Multi-process OOP-R (Out-of-Process Rasterization)**: Blink, Canvas 2D, PDFium, and Views UI do **not** call GPU Skia directly in renderer processes. They record into `cc::PaintCanvas` / `cc::PaintOpBuffer`, serialize commands over IPC to the sandboxed GPU process (`components/viz`), and replay them into Skia there. Remote text relies directly on Skia's `SkChromeRemoteGlyphCache` (`src/text/gpu/`) and `Slug` serialization.
- **Process & platform overrides (`skia/ext/`)**: Chrome replaces Skia's allocator (`SK_USE_PARTITION_ALLOC` / `raw_ptr` / `raw_ref` throughout Skia headers, `SkMemory_new_handler.cpp`), discardable memory (`SkDiscardableMemory_chrome.cc`), logging (`google_logging.cc`), tracing/memory dumps (`event_tracer_impl.cc`, `skia_memory_dump_provider.cc`), and histograms. Static global initializers are banned (`SK_ALLOW_STATIC_GLOBAL_INITIALIZERS=0`).
- **Two-tier codec usage**: Blink maintains `third_party/blink/renderer/platform/image-decoders/` for web images, but increasingly delegates directly to Skia's **Rust** codecs (`rust_png_ffi_cpp`, `rust_bmp_ffi_cpp`, `rust_ico_ffi_cpp`, `rust_jpeg_ffi_cpp` explicitly grant GN visibility to Blink's image decoders!).

### 2.2 Exact Subsystems Compiled by Chrome (`484.9K` Prod SLOC / 85.3% + `6.0K` Experimental Rust)

## 3. How Skia Is Used in Android

Android integrates Skia via Skia's own generator script [`gn/gn_to_bp.py`](../skia/gn/gn_to_bp.py), which produces `Android.bp` / `Android.gen.bp` targets in AOSP `external/skia`. Unlike Chrome's single `//skia` component, Android builds **three distinct Skia configurations** for three different roles.

### 3.1 Three Distinct Consumers in AOSP

1. **`libhwui` (linked against `libskia`) — Android Framework 2D UI & Graphics**:
   - Backs virtually the entire `android.graphics.*` Java/Kotlin and NDK API surface (`Canvas`, `Paint`, `Path`, `PathEffect`, `PathMeasure`, `Shader`, `RuntimeShader` [AGSL = Android Graphics Shading Language, powered by SkSL], `RuntimeXfermode`, `RenderEffect`, `ColorFilter`, `MaskFilter`, `Mesh`, `Picture`, `Region`, `Bitmap`, `BitmapFactory`, `BitmapRegionDecoder`, `ImageDecoder`, `AnimatedImageDrawable`, `Gainmap`/UltraHDR, `ColorSpace`, `Typeface`, `PdfDocument`, `VectorDrawable`, and `RenderNode` display lists). Jetpack Compose renders through `android.graphics.Canvas` → HWUI → Skia.
   - **Deep private-header coupling**: `frameworks/base/libs/hwui/Android.bp` directly adds `external/skia/include/private`, `src/core`, `src/utils`, `src/image`, `src/gpu`, `src/shaders`, and `src/codec` to its `include_dirs`. HWUI is *not* isolated behind Skia's public `include/` ABI.
   - **Desktop host builds for Android Studio LayoutLib**: `gn_to_bp.py` also generates CPU-only builds (`libskia_linux_srcs`, `libskia_mac_srcs`, `libskia_win_srcs`, including macOS `SkImageGeneratorCG` and Windows `SkImageGeneratorWIC`) so Android Studio can run `libhwui` + Skia on developer machines.
2. **SurfaceFlinger `librenderengine` (linked against `libskia_renderengine` + `libskia_renderengine_oopr`)**:
   - Android's system display compositor uses a **stripped-down Skia** for GPU layer compositing, rounded-corner clipping, blurs (Gaussian/Kawase via SkSL), stretch effects, and HDR tonemapping (`MouriMap`, `LinearEffect`, LUT shaders, gainmaps).
   - Actively supports **both Ganesh (GLES + Vulkan) and Graphite (Vulkan)** (`SkiaGLRenderEngine`, `GaneshVkRenderEngine`, `GraphiteVkRenderEngine`).
   - Strips out codecs (JPEG/WebP/GIF/AVIF/JXL/PNG), PDF, FreeType/Fontations, and Expat to minimize binary footprint — except the flagged `RENDERENGINE_OOPR` variant, which re-enables PNG + FreeType + Fontations.
3. **`SkQP` (`CtsSkQPTestCases` / `libskqp_jni`) — Android CTS GPU Conformance**:
   - Ships Skia's own GMs and unit tests inside Android's Compatibility Test Suite (`cts`) to validate OEM OpenGL ES and Vulkan GPU drivers (with Graphite + Vulkan enabled, PDF/Skottie/SVG/FreeType/ICU disabled).

#### D. Compiled-In Dead Weight & Transitional Legacy (Not Counted in "Neither" Above!)
For a Rust migration, two additional categories matter just as much as the 70.7K SLOC of strictly uncompiled code:
1. **Compiled via `.gni` bundling, unused at runtime (~7.2K SLOC)**:
   - `SkSLMetalCodeGenerator` (**3,306 SLOC**) is compiled into *both* Chrome and Android because `skia_sksl_codegen_sources` bundles all four GPU code generators together, yet neither Chrome nor Android uses native Metal.
   - `SkSLWGSLCodeGenerator` (**3,958 SLOC**) is compiled into Android for the same reason, yet Android does not use Dawn/WebGPU.
   - `src/capture/` (**790 SLOC**) is compiled via core/utils targets for diagnostic frame capture rather than normal production rendering.
2. **Transitional legacy being actively deprecated (~147K+ SLOC)**:
   - **Ganesh (~142.7K SLOC)** is only retained in Chrome and Android while **Graphite** finishes rolling out across platforms/devices. A ground-up Rust effort should treat Ganesh as strictly out of scope.
   - **FreeType port (3.9K SLOC)** and legacy **C++ PNG/BMP/ICO/EXIF/ICC** decoders/parsers (~5K SLOC) are already mid-replacement by **Fontations** and **Rust codec crates**.

## 5. Early Takeaways for Migrating Skia to Rust (`skia-rs`)

1. **The effective target is ~300–350K SLOC, not 568K (and nowhere near 1.5M).** Dropping unused modules & GPU backends (70.7K), retiring legacy Ganesh (142.7K), and acknowledging the already-migrating font/codec edge leaves a focused core: **Core + CPU RasterPipeline/Opts + Effects/Shaders (~122K) + Graphite (~60K excl. Metal/experiments) + SkSL (~52K) + PathOps (~21K) + PDF/Utils (~22K) + `skcms` (~4K)**.
2. **Skia's own Rust roadmap already reveals the easiest-to-hardest seam ordering:**
   - *Already in flight (untrusted input parsers)*: **Fontations** (fonts), **Rust codecs** (PNG, BMP, ICO, JPEG, AVIF), **ICC (`moxcms`)**, **EXIF**. These have narrow byte-in/pixels-or-paths-out boundaries and immediate security payoff.
   - *Clean algorithmic islands next*: **`skcms`** (4.3K SLOC, self-contained C/SIMD color math), **`src/pathops/`** (20.6K SLOC, pure geometry — and `modules/bentleyottmann` shows Skia already wants a cleaner replacement), **`src/pdf/`** (9.2K SLOC) & **`src/xps/`** (1.9K SLOC), **`src/sksl/`** (59.1K SLOC — a classic compiler where Rust's algebraic data types shine, or a seam toward `naga`!), and **CPU sparse-strips / Vello-style path rasterization** (which Graphite is already prototyping!).
   - *Hardest seams (tightly coupled state & performance)*: **`src/core/`** (84.4K SLOC) + **`SkRasterPipeline_opts.h`** (6.1K SLOC of hand-tuned multi-ISA SIMD) + **Graphite core/Dawn/Vulkan** (60K SLOC).
3. **ABI & consumer coupling is a major constraint — especially on Android.** Chrome already isolates Skia behind `cc::PaintOpBuffer` and `//skia/ext/`, whereas Android's **`libhwui` directly `#include`s Skia's internal `src/core`, `src/gpu`, `src/image`, `src/shaders`, `src/codec`, and `include/private` headers**. Any incremental Rust migration must either keep C++ shim headers for HWUI (as Fontations and `rust/png` do via `cxx`) or co-evolve HWUI's boundary first.
